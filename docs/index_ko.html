ADK Root ↔ Sub-Agent(BQCA) State·Stateless·Memory·Routing 개선 및 2-Tier Token 최적화 검증

Google ADK Agent를 BigQuery Conversational Analytics(BQCA) 앞에 둘 때 나오는 두 가지 기술 질문을 다룹니다. 1) Root Agent와 BQCA Data Agent 사이의 State·Memory·Routing을 어떻게 설계할 것인가, 2) 각 설계가 두 계층에서 Token을 얼마나 쓰는가. 이 Page의 모든 수치는 Google Cloud에서 측정했습니다. ADK Token은 Vertex AI usage_metadata, BQCA Token은 Cloud Trace 기준입니다.

과제 1: Root·Sub-Agent State · 3-Turn Message Window · Memory · Routing 과제 2: ADK 계층과 BQCA 계층의 Token 실측 측정 시각 (UTC):
과제 1 · State, Memory, Routing

구성별 동작 방식

  • ADK 내장 ask_data_agent: 호출할 때마다 Data Agent 정보를 조회하고, 현재 질문 하나만 BQCA에 보냅니다.
  • 관리형 대화 (ConversationReference): 이력을 서버에 보관하지만 Data Agent 하나에 묶입니다.
  • 이 Repository: Root Router와 Domain별 Sub-Agent 3개, Sub-Agent 간 직접 전환, 병렬 Fan-out, Domain별 3-Turn Message Window, Session State와 Memory Service를 씁니다.
과제 2 · 두 계층의 Token 사용

Token이 쓰이는 곳

  • BQCA 계층: Chat Turn 하나는 보통 내부 LLM 호출 2회로 처리되고, 호출마다 Data Agent에 연결된 Schema와 용어집을 읽습니다. 설명이 붙은 Table을 적게 연결하는 것이 가장 큰 요인입니다.
  • ADK 계층: Prompt는 Instruction, Tool 정의, 재전송되는 Session으로 이루어집니다. To-Be Agent는 고정 Instruction, Sub-Agent당 Tool 1개, 3-Turn 이력, 축약한 Tool 결과를 씁니다.
  • 기억 복원: 이전 Session에 대한 질문은 BQCA 호출 없이 Memory에서 답합니다.

3. As-Is 문제 재현 vs To-Be 해결 직접 대조 시현 및 실시간 단계별 Workbench (S1 – S5)

사전 검증된 기준 실측치(Reference Baseline)가 즉시 표시되며, 각 단계(S1 → S5) 입력창에 직접 질문을 수정·입력하여 실행하면 실제 GCP에서 As-Is(단일 통합 Data Agent에 ADK 내장 data agent Tool을 그대로 사용)와 To-Be가 동시에 실행되며, 답변·SQL과 ADK 계층의 Vertex AI usage_metadata 실측 Token을 나란히 비교할 수 있습니다.
